# ADR 0015 — Translations keyed by the Turkish source string

**Status:** accepted

The dictionary in `src/shared/i18n-en.ts` is keyed by the **Turkish string as it
appears in the code**, not by an identifier like `conn.lost`.

**Why:** two properties fall out of it that matter more than tidiness.

1. Call sites stay readable. `t('Bağlantı kesildi')` says what it renders;
   `t('conn.lost')` sends the reader to a table to find out.
2. A missing entry degrades to Turkish. A half-translated build is ugly; a build
   showing `conn.lost` to a user is broken. There is no state in which the app
   displays a key.

**Cost:** editing the Turkish wording breaks the lookup silently. That is what
`npm run i18n` exists for — it collects every `t('…')` / `m('…')` in the source
and fails if any of them has no English entry. It runs in CI before packaging.

**Placeholders** are `{name}` and are substituted *after* lookup, so a
translation may reorder them. English and Turkish do not agree on word order,
and positional `%s` would have forced the Turkish sentence to follow English
structure.

## Main process

Main has no DOM and no localStorage, so the renderer pushes its choice over the
`dil:degisti` channel at startup and on every change. Until it arrives the
default is Turkish — the same fallback the dictionary uses, so an error raised
during early startup is still readable.

## The one place a ref was needed

`TerminalPane` builds the xterm instance in an effect keyed on `sessionId`.
Adding `t` to that dependency array would tear down and rebuild the terminal on
every language switch, taking the tab's scrollback with it. The translator is
read through a ref instead, updated in its own effect — the messages written
into the terminal use the current language without the terminal being reactive
to it.
